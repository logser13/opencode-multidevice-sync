# Interrupted history policy in 0.2.0-v2.1

The previous isolated fixture contained four V1 histories with five incomplete assistant records already present in V1. They hold 7669 migrated V2 messages. No execution owner, queue, suspended/compacting state or workspace binding exists; embedded tools are completed or errored. An absent completion timestamp alone does not prove current execution.

The adapter preserves these records under an explicit offline boundary. `push --offline` checks the original V2 database journals before a dry-run copy or Git work and then reads a closed immutable snapshot. Import already requires the same offline boundary. Runtime flags, queues, unknown embedded tool state and execution ownership remain blocking. Default/live export and automatic push do not acquire this exemption, and a synced settings file cannot enable it. There is no manual timestamp repair, deleted message, success marker or new shard format.

OpenCode 2.0.29 filters incomplete assistants from native session export, so an API export alone does not prove preservation. The acceptance checks every original raw message row, parses JSON without changing values, compares IDs/types/sequences/timestamps and complete content hashes, then separately compares native API visibility before and after transfer.

Observed native behavior: continuing the session whose last assistant is unfinished causes OpenCode itself to set that old assistant's completion timestamp and time_updated. Its content was not lost, but such a rewrite intentionally fails the adapter's immutable-history rule. Do not weaken that rule or manually undo the native mutation. Keep the original session as an archive and create a native fork immediately before its incomplete assistant. The fork can continue while the source retains the complete original record. The other three histories can be tested for continuation under their existing IDs with prefix validation.

The dedicated `scripts/accept-interrupted-v2.mjs` consumes a diagnostic manifest of exactly four IDs and a previous disposable V2 fixture; it never needs the working database. It uses a local bare Git remote, isolated roots, local model stub and explicit offline CLI push. The fixture project locations are rebound only in the new copy. Tests include native reads, direct/fork continuation at B and A, original prefix retention, parent/fork dependency transfer, full snapshot equality, idempotence, pre-import backups and SQLite checks. Choose a short disposable root, for example `C:/temp/omds-i1`, because Windows SQLite backup filenames need room for temporary journals. The source fixture must be within the same disposable work parent as the isolated development checkout.

```powershell
node --max-old-space-size=2048 scripts/accept-interrupted-v2.mjs --root=C:/temp/omds-i1 --cli=C:/isolated/opencode.exe --plugin-dir=C:/isolated/node_modules/opencode-multidevice-sync --manifest=C:/isolated/work/manifest.json --source-fixture=C:/isolated/work/previous/A/data/opencode/opencode.db
```

The manifest has `sessions` entries with `id`, and `unfinished` entries containing `id` and `laterCompletedAssistants`; the driver identifies the incomplete tail from zero later completions. Actual IDs and conversation text are not embedded in source. A machine-readable report records outcomes and hashes without messages or credentials. A separate raw source-fixture SHA-256 before/after proves it was not modified. API requests use connection-close in the Windows test client to avoid pooled socket reuse during long snapshot hashing. Mutating prompt/fork requests are never retried.

This proves a bounded offline transport scenario, not visual Desktop behavior, compatibility with every provider, or readiness to replace working V1 installations. Both ends need this preview for interrupted history. Keep original backups, migrate loaders/configs separately, and do not mix V1/V2 shard repositories or concurrently edit a conversation on multiple computers.
